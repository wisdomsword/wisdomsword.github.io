结论先行

都江堰最值得保留的工程事实有三条：选择性卸载、硬容量边界、维护制度化。 正文把它们拆成六条主原则（C1–C6），以便逐项执行和验收；十二条启发只作为这些主原则的来源与方法附录。

这套东西在干什么
都江堰是一套分流、排沙和引水工程，约始建于公元前 256 年。现有工程仍承担灌溉和供水任务，但其运行也依赖闸门、水库调度与岁修。
它解决了什么难题
岷江同时带来水、沙和卵石。都江堰把分水、排沙和定期清淤结合起来，减少泥沙进入灌区；长期运行不能归因于单一构件。
它到底怎么做到的
三类机制共同作用：地形、闸门/水库调度和岁修维护：
① 在河弯处劈一道「鱼嘴」，利用水流拐弯时的离心力，让干净的表层水走内江、带沙的底层水走外江；
② 开一个只有 20 米宽的「宝瓶口」当咽喉，把进水量卡死；
③ 在旁边修一道只有 2 米高的矮堰「飞沙堰」，水一大就自动翻过去，顺手把沙卷走。
一个可复核的数字
1970–1973 资料中，外江约分走 36%–39% 的水，悬移质分沙约为 42%–53%。1975–1978 的另一组资料显示，约 74% 的卵石进入外江；两组数据不能当作同年配对。另有转引资料称，到达宝瓶口的泥沙不足总量的 8%，原始试验页码仍待补。
这跟 AI 系统有什么关系
我们现在给 AI 造的「Harness」（套在大模型外面管住它的那层壳）面临相似的压力：过期上下文、重复错误、失败重试和技术债都会积累。这里可迁移的是处理方法：先定义要卸载的对象，再测量卸载效果，并把容量与权限边界放在执行面。
六条原则
C1 测选择性卸载；C2 守住容量边界；C3 建立可重算基线；C4 只用连续信号排序，授权仍走显式规则；C5 给维护任务指定责任人和期限；C6 用下线演练验证替换与隔离。每条原则都要由项目填写验收阈值和证据。

六、「场」的落地设计 对应 C1 选择性卸载、C2 硬容量边界、C3 可验证基线、C4 场信号与显式授权、C5 维护制度化、C6 组合结构与失效隔离

C4 的结论是：场可以减少重复规则，但不能消灭规则、漏判或冲突。 这里说的「场」不是某个 LLM 的上下文窗口管理技巧，而是一个 Harness 系统在真实研发项目里运行所需要的整套结构性环境—— 以 ForgeAgent 这类轻量 LLM agent 为例，它包括：工具注册表与沙箱分级、Golden 验证基线、milestone 治理与 CI 门禁、有界的记忆与上下文。 场的存在，让风险排序获得连续信号；授权仍由显式策略和硬边界决定。

1. 场信号如何减少重复规则（但不替代规则）

维度规则（if-else）场（连续标量）
判据形态离散条件（if-else）连续标量 ρ + 硬边界
规模成本O(N)：需评估 N 个元素并维护规则计算 ρ 仍为 O(N)，可减少重复阈值
未覆盖情况可能漏判，需 deny-by-default 兜底只能作为排序信号，不能自动放行
冲突处理需要优先级仲裁与明确拒绝路径标量排序不消除冲突，仍需规则裁决
验证方式逐条测试测分离度 κ —— 但仅限存在标注有害类的通道（见本节第 5 小节「可验证判据」）；否则用标注评审集测排序质量
失效模式规则腐化、互相矛盾参数漂移或误排序（需独立审计）

研发场景里规则数量会增长，因此可用连续信号减少重复判定；但对未覆盖情况必须 deny-by-default， 并保留优先级、阈值、路由和人工复核，不能声称“没有漏判”。

2. 场的最小定义：给每个项目要素算一个连续标量 ρ

物理场的类比可转成排序信号，但软件授权不能由它自动决定。 对应到 Harness 研发场：给仓库里的每个要素（模块 / 工具 / 依赖 / 任务 / 测试）算连续标量 ρ，供排序、抽样和人工审查使用；爆炸半径另行评估。

ρ_priority(x) = α·冗余度 + β·陈旧度 + γ·失效率 blast_radius(x) = 可触达资产 × 权限等级 × 故障影响范围

符号说明：此处写全 blast_radius(x)，以免与第四节中表示渠道/堰宽的 B 混淆。

输入可以从 git 历史、CI、单元测试与 golden 回归记录采集；权重、阈值和授权规则仍需显式维护：

  • 冗余度：代码 / 配置重复度（复制粘贴模块、重复函数、过度抽象），重复即升高
  • 陈旧度：自最后一次被改动 / 引用以来的步数，按 exp(−Δ/λ) 衰减
  • 失效率：该要素在单元测试与 golden 回归中的失败率（含 flake 率）
  • 引用度：作为相关性和人工审查优先级的旁证，不抵扣风险
  • 爆炸半径：按可触达资产、权限等级和故障影响范围独立计量

ρ 是连续信号，不是授权标签。一个工具或模块可按 ρ 与触达面排序，但 trusted、restricted、untrusted 的路由仍需显式规则、能力边界和人工审查；高引用度不能自动降低风险。

3. 通道的几何：把研发要素从「白名单」改成「河道」

4. 「标准埋在地下」在场上怎么落

卧铁有三个特征：埋在河床下（不在表面）、挖到位才可见（不能口头声称）、是淘滩的标尺（判定标准）。 在研发场中，这三点翻译为：

  • 关键标准应有可重算的基线。系统的「正确状态」不能只靠声明文档；是否采用事件流重放，取决于一致性和审计需求。
  • 验证 = 重算，不是比对声明。缓存与快照只是加速，不是真相。 定期对账：从事件流重新投影，与当前状态比对，不一致即判定漂移。
  • 标尺必须可重复测量。可选 Golden 通过率、哈希 / Merkle 根、单调递增序列号以及延迟、token 数、失败率；具体组合按项目审计要求确定。
落地动作

若项目选择事件流方案，可为关键状态附 state_hash、维护 Golden 集并提供 replay(from_seq)；这些是项目特定方案，不是都江堰必然推出的规范。

5. 硬边界检查应持续执行

飞沙堰的物理特征是：堰顶 728.25 m 是几何常量、水过不去时无法谈判、古训明令「低作堰」禁止加高。 在研发场中翻译为四条：

  • 阈值放在不可运行时修改的位置。内核常量文件 / 只读配置 / 哈希锁定的配置段； CI 门禁要求改动需评审 + 事件留痕。不应出现在 Prompt、文档或 agent 可写的配置里；跨边界仍需硬门禁。
  • 检查执行和检查拒绝是两件事。适用的 ruff、pytest、golden 与沙箱策略应在每次提交或任务中运行；没有拒绝可能表示输入健康，不能单独据此判断阈值高低。
  • 门禁健康度分开统计。至少记录执行覆盖率、真实缺陷检出率、误报率和绕过次数；是否设置目标区间由项目风险决定。
  • 抬高阈值 = 把成本转移到未来。加高堰短期多引水（KPI 好看）、长期排不出沙 （河床抬高 → 系统功能逐步丧失）；对应放宽熔断、跳过 Schema 校验、放行 untrusted 直接执行—— 短期通过率上升，长期系统淤废。
可验证判据

对适用变更，CI 检查执行覆盖率应达到项目登记值；拒绝率不设通用非零目标。越权绕过必须为 0，误报和漏报用标注样本定期复核。κ 只用于已定义有害负载的选择性卸载通道。

  1. 给每个项目要素（模块 / 工具 / 依赖 / 任务）算 ρ，并单列爆炸半径，记录权重、阈值和数据来源

启发 1

分沙比 > 分流比

归属主原则：C1 选择性卸载 · 都江堰原型：分沙比 > 分流比
工程事实

1970–1973 资料给出外江分水 35.8–39.1 %、悬移质分沙 42.3–52.8 %；约 74 % 的卵石推移质来自 1975–1978 资料，不能当作同年配对。

作用机制

分水与分沙是两个解耦的变量。都江堰的精髓不在分水，而在分沙比严格大于分流比。

形式化κ = β_sed / β_water；悬移质无逐年配对数据，保守端点为 42.3/39.1≈1.08 至 52.8/35.8≈1.47。卵石约 1.98 来自另一时期；飞沙堰约 <1.75 是上界，约 1.60 依赖 50% 分流比假设。
结论强度

中：分水、悬移质和卵石数据来自不同观测期；κ 仅作保守端点或分项示例。

适用边界

只适用于承担选择性卸载职责且有害负载可标注的通道；其他通道不得套用 κ。

回到主原则：C1 选择性卸载
启发 2

飞沙堰 728.25 m 是硬编码

归属主原则：C2 硬容量边界 · 都江堰原型：飞沙堰 728.25 m 是硬编码
工程事实

飞沙堰堰顶高程 728.25 m。此处有两个不同的「两米」，不可混为一谈：一是堰体高出河床的结构高度（约 2 m，第一节数据表内记作 2.15 m），二是古训另立的规则——“堰顶只能高出内江卧铁 2 米”。

作用机制

在被动几何模型中，溢流由高程触发；现实运行还受闸门、调度和维护制度影响，不能把模型触发器当作完整控制逻辑。

形式化q_spill = m·B·√(2g)·H^{3/2}，H = z_water − 728.25 m。以 B=240 m 为情景时，q=1 000 m³/s 对应 H≈1.81 m，q=2 000 对应 H≈2.88 m；这不是现场水位复算。
结论强度

中：堰顶高程有资料支持；堰宽口径未统一，流量—水头值属于公式情景。
