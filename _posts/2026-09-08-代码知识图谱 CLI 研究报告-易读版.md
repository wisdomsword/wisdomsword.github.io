# 代码知识图谱 CLI 研究报告（易读版 · 修订 v4）

> 初始调研：2026-06-25 ｜ **全面核验：2026-09-02** ｜ 视角：CLI + MCP 双形态（以 CLI 为可复现基准；核心探索能力同源，接口面因形态不同）｜ 适用：Harness 工程团队
> 评估对象：**CodeGraph / GitNexus**（同类「代码知识图谱 CLI」；Graphify 属「人类向多模态知识图谱」非同类，已移出候选集）
> 仓库链接：CodeGraph → https://github.com/colbymchenry/codegraph ｜ GitNexus → https://github.com/abhigyanpatwari/GitNexus
> **证据说明（原 `[核查]` 标记已全部移除）**：2026-09-02 完成全量核验——CodeGraph 用**本机 v1.6.0 实跑**（`--help`、`install --print-config`、`status`）+ **LICENSE 原文** + **GitHub API**；GitNexus 用 LICENSE 原文 + README + GitHub API（未本机安装，因许可已否决）。仅保留 `[上游报告]`（上游声称、未独立复现）与 C 级（量级感知）两种标注。

## 两工具综述（开篇导读）

### CodeGraph 综述（推荐）
**一句话**：本地优先的代码语义知识库——把函数/类/变量/接口/配置项等符号的**定义与调用关系**建成可查询索引，经 **MCP** 开放给 Coding Agent。纯 AST、**无 LLM、无 API key、100% 本地**（SQLite + WAL）。

| 维度 | 说明 |
|------|------|
| 符号索引 | 函数定义/调用、类继承与成员、变量/常量定义点、接口/配置项声明 + **框架路由感知**，纯 AST（tree-sitter 编译进 Rust 内核） |
| 查询接口（MCP） | 默认**只有 `codegraph_explore`**；另 7 个（`node`/`search`/`callers`/`callees`/`impact`/`files`/`status`）功能完整但**默认隐藏**，用 `CODEGRAPH_MCP_TOOLS` 启用 |
| MCP 传输 | **仅 stdio**（`codegraph serve --mcp`）。`serve` 选项只有 `--mcp`/`--path`/`--no-watch`，**无 HTTP、无 TCP** |
| 部署形态 | **每项目独立、由 agent 以 stdio 拉起**；无 Docker 网关、无多项目统一端口（那是 GitNexus 的能力） |
| Agent 集成 | `codegraph install` 自动为 **9 类 Agent** 写 MCP：**Claude Code、Cursor、Codex CLI、opencode、Hermes Agent、Gemini CLI、Antigravity IDE、Kiro、GitHub Copilot** |
| 典型场景 | ①代码理解（查定义/调用链/数据流/模块解释）；②代码操作（定位 bug、改前评估影响、评审定位）；③Agent 集成（作「代码记忆」） |

> **Claude Code 接入**（经 `codegraph install --print-config claude` 逐字取证）：
> - 自动：`codegraph install --yes`（写 `~/.claude.json` + 权限白名单）
> - 手动：`~/.claude.json` 加 `mcpServers.codegraph = {type:"stdio", command:"codegraph", args:["serve","--mcp"]}`；`~/.claude/settings.json` 加 `"permissions.allow":["mcp__codegraph__*"]`
> - 子代理：安装器另向 `CLAUDE.md`/`AGENTS.md`/`GEMINI.md` 写 marker，教它们用 `codegraph explore` CLI（子代理看不到 MCP guidance）
>
> **CLI 与 MCP 等价（已确认，不再是存疑项）**：`codegraph --help` 与 README 均明写 `explore` 为 *"same output as the `codegraph_explore` MCP tool"*。

### GitNexus 综述（对照，能力完整但因许可不采用）
**一句话**：深度代码智能引擎——符号图 + CFG/CDG/到达定义 + **PDG/污点**（`--pdg`，默认关闭、实验性、仅 TS/JS）。MCP 工具面（17 个）远多于 CodeGraph，且支持 **HTTP 多仓库服务端部署**。

| 维度 | 说明 |
|------|------|
| 查询接口（MCP） | **17 个工具**（15 per-repo + 2 group）：`list_repos`/ `query`/ `context`/ `impact`/ `trace`/ `detect_changes`/ `check`/ `rename`/ `cypher`/ `route_map`/ `tool_map`/ `shape_check`/ `api_impact`/ `explain`/ `pdg_query` + `group_list`/ `group_sync`；另含 Resources 与 2 个 prompts |
| MCP 传输 | **两种**：stdio（`gitnexus mcp`）+ HTTP（`gitnexus serve`，端口 **4747**） |
| 部署形态 | **多仓库统一服务端**：global registry，一个 MCP server 服务多个已索引仓库，**免 per-project 配置**；有 Docker 镜像 |
| Agent 集成 | `gitnexus setup` 自动探测并写入全局配置；覆盖 Claude Code/Cursor/Antigravity/Codex/OpenCode/Windsurf/CodeBuddy(腾讯)/Qoder(阿里) 等；**Claude Code 与 Codex 集成最深**（+skills+hooks） |
| 关键限制 | **PolyForm Noncommercial 1.0.0 限制商业使用** → 对商业 Harness 工程**硬阻断** → 不采用 |

> **综述要点**：两者均提供 CLI 与 MCP，核心探索能力同源，但工具数量、传输与部署接口不同。CodeGraph 差异化＝「**单强工具 + 默认增量 + 零依赖 + MIT**」；GitNexus 差异化＝「**深度分析 + 17 个 MCP 工具 + HTTP 多仓库**」——但被 **PolyForm Noncommercial** 锁死，商业场景不可用。

## 结论先行（推荐方案）

**CLI + MCP 双形态 + 单押 CodeGraph，不采用 GitNexus。**（结论对 MCP 与 CLI 用户同样成立）

| 工具 | 判定 | 一句话理由 |
|------|------|-----------|
| **CodeGraph** | ✅ 主力（Agent + CI） | **MIT 可商用**、安装最稳（Rust 自包含、零前置依赖）、增量**默认开启且真增量已落地**、`affected` 直出测试集、单命令 `explore` 高密度检索 |
| **GitNexus** | ❌ 不采用 | **PolyForm Noncommercial 1.0.0（LICENSE 原文核验）限制商业使用＝硬阻断**；PDG/污点仍实验性，真增量索引尚未落地 |

**落地节奏**：先只上 CodeGraph 跑两周 → 主 Agent 走 MCP、子 Agent/CI 走 CLI → CI 接 `codegraph affected` → 单维护者风险写入团队文档。不采用 GitNexus。

## 3. CLI vs MCP — 先决判断

**MCP 与 CLI 是同一引擎的两种接入形态，核心探索能力同源、二者均有效；但接口面并不完全相同：**

- **MCP（交互式编码 Agent）**：适合 IDE 内交互式编码 Agent（Claude Code / Cursor / Codex / 等 9 类）。CodeGraph 经 `codegraph install` 自动注册（`codegraph serve --mcp` 拉起），默认单工具 `codegraph_explore`；GitNexus 提供 `gitnexus mcp` / `gitnexus serve`。
- **CLI（自动化 / CI / 子代理 / 非 MCP 宿主）**：适合流水线、CI、批量、子代理等可脚本、可复现场景。`codegraph explore` 与 MCP `codegraph_explore` 输出一致；`affected` 等 CLI 能力并非 MCP 工具的逐项镜像。
- **以 CLI 为基准**仅因 CLI 在 CI/批量中可脚本化、可复现、易测量；**不等于** MCP 在 Coding Agent 中无效。选型结论对两种接入形态都成立。

> 与《Harness 工程上下文》一文一致：MCP 给主 agent、CLI 给子代理与 CI，二者同源互补，而非互斥。

## 3.5 与 Coding Agent 的集成（重点 · Claude Code / Codex / Cursor 等）

> **为什么是重点**：工具价值 90% 在「主 Agent（IDE 内交互式）走 MCP、子 Agent / CI 走 CLI」的协同。

### A. CodeGraph（推荐，接入最省心）
```bash
codegraph install                      # 自动探测已装 agent
codegraph install --yes --target=auto  # 非交互式
codegraph install -i --yes             # 顺带对当前目录建索引
codegraph install --print-config claude  # 只打印配置不落盘（便于审计）
```
安装器同时向 `CLAUDE.md`/`AGENTS.md`/`GEMINI.md` 写 marker，教子代理用 `codegraph explore` CLI。

**各 Agent 落盘位置（`--print-config` 实测取证）**：

| Agent | 配置文件 | 传输 |
|-------|---------|------|
| Claude Code | `~/.claude.json` | stdio，`args: ["serve","--mcp"]` |
| Cursor | `~/.cursor/mcp.json` | stdio，带 `--path ${workspaceFolder}` |
| Codex | `~/.codex/config.toml` | stdio（TOML 格式） |
| opencode | `~/.config/opencode/opencode.jsonc` | `type: "local"` |

**MCP 工具开关**：默认只有 `codegraph_explore`；其余 7 个用环境变量启用，且被 `mcp__codegraph__*` 通配符自动放行：
```bash
CODEGRAPH_MCP_TOOLS=explore,node,search,callers codegraph serve --mcp
```

### B. GitNexus（能力完整，但因许可不采用）
```bash
gitnexus setup                  # 自动探测编辑器写全局配置
gitnexus setup -c cursor,codex  # 只配指定集成
```
`analyze` 一条命令完成：建索引 + 装 skills + 注册 Claude Code hooks + 生成 `AGENTS.md`/`CLAUDE.md`。17 工具 + HTTP 多仓库服务端适合中心化部署——但 **PolyForm Noncommercial 限制商业使用**，不可用。

### C. 推荐协同拓扑
```
IDE 主 Agent (Claude Code/Codex/Cursor)  ──MCP(stdio)──▶  codegraph_explore（单工具，自适应）
   ├─ 子 Agent / 非 MCP 宿主  ──CLI──▶  codegraph explore / affected（与 MCP 输出一致）
   └─ CI 流水线  ──CLI──▶  codegraph init && codegraph affected  → 测试左移
```

## 5. 规模与性能（实测替换估算）

### 5.1 索引体积：本机实测（A 级，09-02）

原「5,000 文件约 30MB」为**无源 C 级估算，已被实测推翻**：

| 样本仓库 | 文件 | 节点+边 | 索引体积 | **每(节点+边)** | 每文件 |
|---------|---:|---:|---:|---:|---:|
| openclaw（TypeScript 应用仓库） | 3,652 | 245,887 | **176.57 MB** | **753 B** | 50.7 KB |
| harness（含 790 KB 打包 runtime） | 49 | 83,366 | **77.66 MB** | **977 B** | **1.58 MB** |

> **取证**：两仓库分别跑 `codegraph status` 读 `Index Statistics`，并用 `ls -la codegraph.db`（185,151,488 B / 81,428,480 B）与 `du -sh` 交叉核对，三者一致；证实 `DB Size` 单位为 **MiB**。索引分别建于 08-29 / 08-27，**体积读数于 09-02 采集**（测的是既有索引体积，**未做冷索引计时**）。
>
> **两条结论**：
> 1. **体积由「节点+边」决定，不是文件数**——每图元素稳定在 **0.75–1.0 KB**；而**每文件相差 31 倍**（harness 仅 49 文件却产出 11,556 个 function 节点）。
> 2. **不可用「文件数 × 系数」外推**。此前依单样本给出的「≈48 KB/文件」已作废。容量规划：跑 `codegraph status` 读出 Nodes+Edges，按 **~1 KB/图元素** 估算；或参照 openclaw 这类常规仓库的**数百 MB** 量级。

### 5.2 性能 `[上游报告]`（未独立复现）

| 场景 | CodeGraph 上游数字 |
|------|-------------------|
| Swift compiler（27k 文件）冷索引 | 约 100 秒 |
| 单文件重同步 | 约 4 秒 |
| Linux kernel（70k 文件 / 2M 符号 / 6.4M 关系） | <12 分钟（2 核 6GB VPS） |
| 7 仓库 Agent 对照（Excalidraw ~640 文件） | 2 vs 43 次工具调用；45s vs 2m42s；整体工具调用 -88%、token -62% |

### 6.3 CodeGraph 得分轮廓（10 分制，非权重）

```
Incremental Index  ██████████ 10   ← 唯一满分（开箱即增量 + 真增量已落地）
Retrieval          █████████░  9
Context Quality    █████████░  9
```

## 8. 团队落地路径

**最小可用方案（推荐起点）**：先只上 CodeGraph，跑两周。

```text
Day 1:    安装 CodeGraph（codegraph install --yes）+ 建 CodeRAG.md + 改团队 Agent 文档引用
Week 1-2: 试运行观察（主 Agent 走 MCP，子 Agent/CI 走 CLI，CI 接 codegraph affected）
评估点:   索引体积（按 ~50KB/文件 预留）/ 增量延迟 / CI 提速是否达标？
```

**索引共享模型**：`.codegraph/codegraph.db` 不入 git（各自本地 daemon 重建 + 连接对账追平）。体积在**数百 MB 量级**，进 git 会拖慢 clone 并产生合并冲突。

**CI 缓存**：**不可按文件数估算**（实测每文件相差 31 倍）。先在目标仓库跑一次 `codegraph status` 读出 Nodes + Edges，按 **~1 KB/图元素** 预估，再据此设定缓存配额。
